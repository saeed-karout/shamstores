**التاريخ:** 2026-09-03
**الفرع:** `ui-ux/storefront-redesign`
**النطاق:** الواجهة الخلفية (Express + Prisma) والواجهة الأمامية (React + Vite) وتجهيز النشر

## 1. الثغرات الحرجة (مُصلحة)

### 1.1 استيلاء كامل على أي حساب عبر مسار عام
**الخطورة: حرجة**

`POST /api/auth/reset-password` كان مسجّلاً بلا أي مصادقة، ويعيد تعيين كلمة مرور
أي مستخدم بمجرد معرفة بريده الإلكتروني:

```ts
const { email, newPassword } = req.body;
const user = await UserService.findByEmail(email);
await UserService.update(user.id, { password: hashedPassword });
```

أي شخص على الإنترنت كان يستطيع الاستيلاء على حساب السوبر أدمن.

**الإصلاح:** المسار صار يتطلب كود تحقق مُرسلاً إلى البريد نفسه، وأُضيف
`POST /api/auth/forgot-password` لطلب الكود، مع رد موحّد لا يكشف البريد المسجّل،
وحد معدل صارم على الاثنين.

### 1.2 تجاوز بين المستأجرين (IDOR) في إدارة موظفي المتاجر
**الخطورة: حرجة**

```ts
router.post('/stores/:storeId/staff', authorize(['super_admin', 'owner']), createStoreStaff);
```

الدور `owner` مسموح، والمتحكّم يستخدم `req.params.storeId` مباشرة دون التحقق من
الملكية. مالك المتجر (أ) كان يستطيع قراءة موظفي المتجر (ب) وحذفهم — بل **إنشاء
حساب موظف بكلمة مرور يختارها داخل متجر لا يملكه**، أي دخول كامل إلى مستأجر آخر.

**الإصلاح:** حراسة `requireBusinessOwnership('store', 'storeId')` على المسارات السبعة.

### 1.3 التحقق من الدومين المخصص كان صورياً
**الخطورة: عالية**

```ts
export const verifyCustomDomain = async (req, res) => {
  const updatedStore = await prisma.store.update({
    data: { customDomain, customDomainVerified: true, customDomainVerifiedAt: new Date() }
  });
  res.json({ success: true, verified: true });
};
```

لا فحص DNS إطلاقاً. أي تاجر كان يستطيع «توثيق» أي نطاق يكتبه — بما فيه نطاقات
جهات أخرى — واحتكاره في قاعدة البيانات (`customDomain` فريد).

**الإصلاح:** تحقق DNS حقيقي في `services/domain.service.ts`: سجل `TXT` على
`_shamstores-verify.<domain>` لإثبات الملكية + سجل `CNAME`/`A` للتوجيه. النطاق لا
يُفعَّل قبل نجاح الفحصين، ولا يُخدَم أي نطاق غير موثّق. ومُنع استخدام نطاق المنصة
نفسه أو عناوين IP أو نطاقات عامة شهيرة.

### 1.4 التلاعب بالأسعار في مسار الطلب العام
**الخطورة: حرجة (سلامة مالية)**

`POST /api/orders` مسار عام، وكان يثق بالعميل في كل ما يخص المال:

```ts
price = item.price || Number(menuItem.price);   // سعر العميل يفوز
const finalTotal = total !== undefined ? total : calculatedTotal;
subtotal: subtotal || calculatedTotal,
discountAmount: discountAmount || 0,
```

أي زائر كان يستطيع شراء أي صنف بأي مبلغ، أو إرسال `total: 0` لطلب بأي قيمة.

**الإصلاح:** الأسعار تُقرأ من قاعدة البيانات حصراً، والمجموع الفرعي والخصم
والإجمالي تُحسب على الخادم، والخصم يُشتق من الكوبون المُتحقَّق منه لا من العميل،
ورسوم التوصيل مثبّتة عند قيمة غير سالبة، مع تحقق من الكمية.

**تحقق عملي:** طلب مزوّر بـ `price: 1` و`total: 0` سُجّل في قاعدة البيانات
بـ `subtotal: 90000, total: 90000` (السعر الحقيقي من قاعدة البيانات).

### 1.5 متابعة طلبات مستأجر آخر عبر Socket.IO
**الخطورة: متوسطة**

`subscribe:order` كان يضم أي مستخدم موثّق إلى غرفة أي طلب بمجرد معرفة معرّفه.
**الإصلاح:** فحص صلاحية الوصول للطلب قبل الاشتراك.

### 1.6 Socket.IO CORS يعود إلى `*` مع credentials
**الخطورة: متوسطة**

عند غياب `SOCKET_CORS_ORIGIN` و`CLIENT_URL` كانت الدالة تُرجع `'*'` — أي موقع
يفتح اتصالاً باسم المستخدم. **الإصلاح:** قائمة نطاقات صريحة، بلا `*` إطلاقاً.

## 3. أعطال وظيفية كانت تمنع الميزات من العمل (مُصلحة)

### 3.1 وضع الصيانة معطّل تماماً
`app.use(maintenanceMiddleware)` كان مسجّلاً **بعد** كل المسارات، فلا يُنفَّذ إلا
للمسارات غير الموجودة. تفعيل وضع الصيانة من لوحة الأدمن لم يكن يؤثر على شيء.
**الإصلاح:** نُقل قبل المسارات، مع ذاكرة مؤقتة 30 ثانية بدل استعلامين لكل طلب.

### 3.2 تسجيل مطعم جديد يفشل دائماً
```ts
let user;
const restaurant = await prisma.restaurant.create({ data: { userId: user.id, ... } });
```
`user` غير معرّف بعد. كل محاولة تسجيل مطعم كانت ترمي `TypeError` وتعيد 500.
**الإصلاح:** إنشاء المستخدم أولاً ثم المطعم، مع slug فريد.

### 3.3 مسارات الدومين المخصص غير مركّبة
`customDomainRoutes.ts` و`customDomainController.ts` موجودان منذ البداية لكن
لم يُركَّبا في `server.ts` إطلاقاً. لم يكن للمطاعم أي طريقة لضبط دومين مخصص.
**الإصلاح:** رُكِّبت على `/api/custom-domain` وأُعيدت كتابتها بتحقق حقيقي.

### 3.4 الكوبونات معطّلة بالكامل
`createCoupon` كان يكتب سبعة أعمدة غير موجودة في المخطط
(`description`, `usedCount`, `validFrom`, `validUntil`, `createdBy`,
`isStoreOnly`, `isRestaurantOnly`) فيرمي Prisma ويفشل إنشاء أي كوبون بخطأ 500.
واستعلام الكوبون في `createOrder` كان يستخدم `validUntil`/`usedCount` كذلك، فأي
طلب يحمل كوبوناً كان يفشل. **الإصلاح:** التسمية الصحيحة
(`startDate`/`endDate`/`usageCount`)، وكوبون بلا تاريخ انتهاء صار يبقى صالحاً.

### 3.5 رموز QR تقود إلى صفحة 404
مولّد رموز QR يعيد `https://shamstores.com/<slug>` عند غياب subdomain أو دومين
مخصص، لكن `App.tsx` لم يكن يحتوي أي مسار لـ `/:slug`. المكوّنات `PublicMenu`
و`PublicTable` و`PublicItem` و`PublicProduct` كانت **مستوردة دون أن تُستخدم في
أي مسار**. **الإصلاح:** مكوّن `PublicStorefrontRoute` ومسارات `/:slug` و
`/:slug/table/:tableId` و`/:slug/item/:itemId` و`/:slug/product/:productId`.

### 3.6 أربعة مسارات أدمن ميتة
`/global-products` و`/restaurants/all-products` و`/stores/all-products` مسجّلة
**قبل** `router.use(authenticate)`، فكانت تُرجع 401 دائماً.

### 3.7 إجبار تسجيل الدخول قبل الطلب
`submitOrder` كان يحوّل الزائر إلى صفحة الدخول، بينما `POST /api/orders` عام
أصلاً. **الإصلاح:** الطلب كضيف بالاسم والهاتف؛ تسجيل الدخول اختياري لـ«طلباتي».

### 3.8 الطلب من واجهة مطعم بلا طاولة مستحيل
الخادم يحدد المطعم من `tableId` أو من حساب المستخدم فقط، ولا يقبل `restaurantId`
من جسم الطلب. طلبات الاستلام والتوصيل من واجهة المطعم كانت ترجع
«معرف المطعم أو المتجر غير موجود». **الإصلاح:** قبول `restaurantId` مع التحقق منه.

### 3.9 اللوح السفلي يشلّ الصفحة بعد الإغلاق
اكتُشف أثناء التشغيل الفعلي: `AnimatePresence` كانت تنتظر حركة خروج نابضة على
قيمة نسبية لا تكتمل، فيبقى غلاف اللوح فوق الصفحة ويبتلع كل النقرات.

### 3.10 استنتاج النطاق في الواجهة يكسر الدومينات المخصصة
`getCurrentSubdomain` كان يعتمد على عدّ أجزاء المضيف: `mystore.com` (جزآن) يُعتبر
الدومين الرئيسي فيُحوَّل الزائر إلى صفحة الدخول، و`shop.mystore.com` يُعتبر
subdomain اسمه `shop`. **الإصلاح:** كل المنطق يقاس على `APP_DOMAIN`.

## 4. الأداء

| المقياس | قبل | بعد |
|---|---|---|
| الحزمة الرئيسية | 2,304 kB (583 kB مضغوطة) | 397 kB (117 kB مضغوطة) |
| عدد الصفحات المُحمَّلة عند فتح قائمة طعام | ~70 صفحة لوحة تحكم | صفحات المتجر فقط |

`React.lazy` لكل صفحات لوحات التحكم، و`manualChunks` لفصل recharts و firebase و
framer-motion و socket.io و dnd و qrcode. إضافةً إلى `compression` على الخادم،
وهيكل انتظار (skeleton) بدل شاشة تحميل تحجب العرض الأول، وصور `lazy` بأبعاد ثابتة.

## 5. النطاقات المخصصة — المسار الكامل الآن

1. التاجر يفتح تبويب «الدومين» في الإعدادات → `GET /api/custom-domain/status`
2. يضبط رابطه الفرعي مع فحص توفر لحظي → `PUT /api/custom-domain/subdomain`
3. يُدخل نطاقه ويضغط «تحقق وفعّل» → `POST /api/custom-domain/verify-domain`
   - الخادم يفحص `TXT` على `_shamstores-verify.<domain>` (إثبات ملكية)
   - ويفحص `CNAME`/`A` (توجيه فعلي إلى المنصة)
   - لا تفعيل قبل نجاح الاثنين
4. زائر يفتح `https://mystore.com`
   - `isCustomDomain()` في الواجهة يكتشف أنه ليس نطاق المنصة
   - `GET /api/public/resolve-host?host=mystore.com` يعيد الـ slug
   - `extractSubdomain` في الخادم يحل النشاط التجاري من المضيف
   - CORS يسمح بالنطاق لأنه موثّق

**خطوة يدوية باقية:** إضافة النطاق إلى Heroku (`heroku domains:add`) ليصدر له
شهادة SSL. تُؤتمت لاحقاً عبر Heroku Platform API أو Cloudflare for SaaS.
راجع `docs/deployment/heroku.md` القسم 8.

## 6. ما تم التحقق منه عملياً

- ✅ `npx tsc --noEmit` في الواجهة الخلفية: نظيف
- ✅ `npm run build` في الواجهة: ينجح — أخطاء TypeScript السابقة 384 كما هي (لم أُضِف أياً منها)
- ✅ الخادم يقلع ويحمّل كل المسارات (اختبار إقلاع بقاعدة بيانات وهمية)
- ✅ 21 حالة اختبار لمنطق تحقق النطاقات: كلها ناجحة
- ✅ ترويسات الأمان حيّة: `X-Content-Type-Options` و`X-Frame-Options` و`Referrer-Policy` و`Cross-Origin-*`، و`X-Powered-By` مُزال
- ✅ حد المعدل على الدخول: 10 محاولات ثم `429`
- ✅ مسار API غير موجود يعيد JSON لا HTML
- ✅ واجهة المتجر تعمل على الجوال (375×812) بلا أخطاء في الطرفية
- ✅ مسار الطلب الكامل: إضافة صنف → لوح الخيارات (سعر حيّ) → شريط السلة → لوح
  السلة → **طلب كضيف بلا تسجيل دخول** وصل إلى قاعدة البيانات بـ `createdBy: null`
- ✅ منع التلاعب بالأسعار: طلب مزوّر سُجّل بالسعر الحقيقي
- ✅ فتح/إغلاق الألواح السفلية ثلاث دورات بلا تراكم وبلا شلّ الصفحة

## 7. ما لم يُختبر بعد

- تدفق استعادة كلمة المرور الجديد من طرف إلى طرف (يتطلب SMTP مضبوطاً)
- التحقق الفعلي من DNS مقابل نطاق حقيقي (منطق الفحص مُختبَر، لا نطاق متاح)
- واجهة المتجر (`StorePublicMenu`) — خارج نطاق المرحلة الأولى حسب المواصفة
- النشر الفعلي على Heroku

## 8. مسائل مفتوحة يُنصح بمعالجتها

| # | المسألة | الأثر |
|---|---|---|
| 1 | **384 خطأ TypeScript سابق** في الواجهة، و`strict: false` في الخلفية | `vite build` لا يفحص الأنواع، فالأخطاء تصل إلى الإنتاج |
| 2 | **لا توجد ملفات migration** — المشروع يعتمد `prisma db push` | لا يمكن التراجع عن تغيير مخطط، وخطر فقد بيانات على الإنتاج |
| 3 | **لا توجد اختبارات آلية** إطلاقاً | كل تحقق يدوي |
| 4 | مطعم ومتجر يتشاركان نفس الـ slug (`tswok`) في البيانات الحالية | `getBusinessBySlug` يعيد المطعم دائماً؛ المتجر غير قابل للوصول بذلك الرابط |
| 5 | التوكن مخزّن في `localStorage` | عرضة لـ XSS؛ الأفضل httpOnly cookie مع CSRF |
| 6 | `checkPlanFeature` يسمح تلقائياً لأي خطة مدفوعة بميزات غير معرّفة | قد يمنح ميزات غير مقصودة |
| 7 | `MenuItem` لا يحتوي حقول `sizes`/`addons` في المخطط | لوح الخيارات يعرض الكمية والملاحظات فقط حتى تُضاف |
| 8 | العملة الافتراضية في المخطط `SAR` بينما المواصفة تطلب `SYP` | مؤجّل إلى المرحلة الثالثة حسب المواصفة |
| 9 | `frontend/.env` كان مُتتبَّعاً في Git (أُزيل من التتبع الآن) | مفتاح Firebase العام موجود في تاريخ Git — لا يحتاج تدويراً لأنه عام بطبيعته، لكن احمِ المشروع بقواعد Firebase ونطاقات مصرّح بها |
